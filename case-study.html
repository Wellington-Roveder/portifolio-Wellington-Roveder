Case study técnico

FechaBot.
Da dor real à arquitetura.

Como um "cientista de dados de bolso" para pequenos e médios negócios foi arquitetado, construído e endurecido em segurança — do zero até um pipeline validado ponta a ponta com entrega real no WhatsApp.

O contexto

O problema

Grandes empresas têm equipes de dados e ferramentas como Power BI. Pequenos e médios negócios — franquias, clínicas, distribuidoras, redes de varejo — fecham o dia numa planilha Excel e não têm equipe técnica pra transformar isso em informação útil, na hora certa, pra quem precisa decidir.

O FechaBot existe pra fechar essa lacuna: ler a planilha que o negócio já usa, aplicar as regras que fazem sentido pra ele, e devolver a resposta no canal que ele já olha — o WhatsApp — com histórico consultável por IA.

A solução

O que o FechaBot faz

Três camadas, cada uma resolvendo uma parte específica do problema.

01 — Automação

Fechamento automático

Lê a planilha do negócio, aplica os filtros configurados e dispara o resumo formatado no WhatsApp, no horário certo — sem intervenção manual.

02 — Persistência

Histórico inteligente

Cada fechamento vira um registro persistido: banco de dados relacional + planilha original preservada no armazenamento de objetos.

03 — IA

Analista sob demanda

O gestor conversa em linguagem natural com os próprios dados — como se tivesse um cientista de dados pessoal, sempre isolado por tenant.

Raciocínio técnico

Destaques técnicos

Cinco decisões representativas do nível de raciocínio envolvido — cada uma detalhada como ADR no repositório.

ADR · Sessão

Modelo de sessão sem confiar só no JWT

Cookie httpOnly + CSRF double-submit + allowlist de sessão via Redis, pra que uma sessão possa ser revogada de verdade — não só do lado do cliente — antes da expiração natural do token.

ADR · Integração

Intenção do cliente vs. realidade externa

Quando a Meta reclassifica a categoria de um template do WhatsApp automaticamente, o sistema rastreia requested_category (o que o cliente escolheu) e effective_category (o que está valendo de fato) como fontes de verdade distintas, com histórico completo.

ADR · Pipeline

Envio assíncrono e resiliente

Fila via Celery, retry automático, e toda tentativa — sucesso ou falha — deixa rastro persistido. Nada é descartado silenciosamente.

Processo

Segurança como processo, não evento único

Múltiplos ciclos de revisão dedicados, cada um com achados documentados, correção aplicada e teste de verificação — não uma auditoria única no fim.

Arquitetura

Isolamento multi-tenant como regra estrutural

Todo dado tem tenant_id; toda rota autenticada filtra por ele a partir do JWT — nunca de parâmetro de requisição. Regra sem exceção, do banco à API.

Engenharia de verdade

CI/CD e disciplina de testes

Todo push passa por um pipeline automatizado antes de ir pra branch principal — lint, aplicação de schema de banco e suíte de testes com cobertura mínima travada.

66
Testes automatizados rodando a cada push — cobrindo webhook, filtros, processamento, serviços e armazenamento
46,9%
Cobertura de código atual, subindo sprint a sprint — piso travado em 40% no pipeline (build quebra abaixo disso)
21
Execuções de workflow no GitHub Actions até agora, incluindo falhas reais corrigidas antes do merge
Pipeline

Gate de qualidade, não só "rodou"

O pipeline aplica o schema do banco, roda lint (ruff) e só então executa a suíte com pytest --cov. Se a cobertura cair abaixo de 40%, o build quebra — a régua sobe aos poucos, junto com os testes novos, em vez de perseguir um número bonito sem substância.

Processo

Falha faz parte do processo, documentada

O histórico de execuções mostra PRs que quebraram o CI e foram corrigidos antes do merge — como o webhook retornando 500 em vez de 400 para payload malformado, pego pelo próprio pipeline antes de chegar em produção.

Sobre este case study

Por que documentei assim

Sou estudante de Ciência da Computação (Anhanguera SJC, 3º semestre) em transição de carreira para desenvolvimento de software. Antes disso, passei cerca de uma década em gestão operacional — bagagem que hoje se traduz menos em "anos de experiência" e mais em hábitos que aplico diariamente no código: comunicar decisões com clareza, priorizar sob pressão, documentar o porquê das coisas e trabalhar bem debaixo de prazo.

O FechaBot é o projeto onde mais apliquei isso: cada sprint documentado, cada decisão de segurança justificada, cada erro tratado como aprendizado registrado — não escondido.
